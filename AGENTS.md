# AGENTS.md

This document explains the purpose, philosophy, boundaries, and working conventions
of this repository for AI coding agents.

For cross-repo architecture and conventions shared across all three repos
(legoESM, legoESM-ocean-runners, this ledger), see `workspace-conventions.md`
(also symlinked to the workspace root as `AGENTS.md` via `bin/setup-workspace`).

## 1. Purpose

This repository is a **personal experiment ledger** for tracking ocean simulations run
with [legoESM](https://github.com/climate-federation/legoESM) via
[legoESM-ocean-runners](https://github.com/lesommer/legoESM-ocean-runners).

It records **what was run, where, how, and what came of it** — not the model code,
not the runners, and not the output data.

**Reproducibility is the core guiding principle.** Every experiment must be
reconstructable from its provenance records. The full chain
`run.yaml → config.yaml → experiment.tag` must be complete and unbroken for every
experiment. If an experiment cannot be reproduced from what is committed, the system
has failed.

Its goals (in priority order):

1. **Reproducibility** — every completed experiment has an `experiment.tag` with
   enough information to reconstruct the exact software environment
2. **Cross-machine synchronisation** — design experiments locally, push, pull on a
   remote HPC machine, run, push back the provenance records
3. **Auditability** — see at a glance what experiments exist, their status, and which
   machine they ran on

## 2. Philosophy

**Reproducibility chain.** The following chain must be unbroken for every experiment:

```
run.yaml (intent) → config.yaml (resolved) → experiment.tag (provenance)
                                                       ↕
                                          runner_tag resolves to a tag in
                                          legoESM-ocean-runners, which pins
                                          the exact legoESM commit
```

- `experiment.tag` is the permanent reproducibility record — never delete or modify it.
- `runner_tag` in `experiment.tag` must resolve to a validated tag in
  `../legoESM-ocean-runners`. If it reads `untagged`, the chain is broken.
- Never commit an experiment directory that is missing `config.yaml` or
  `experiment.tag` after the experiment has been run.

**Experiments as data, not code.** This repo contains declarative specs (`run.yaml`)
and generated provenance records (`experiment.tag`, `config.yaml`). It does not
contain model code, runner code, or simulation output.

**Git as the transport.** Synchronising between your laptop and an HPC machine means
`git pull` / `git push`. The `run.yaml` file is the portable unit of intent — write
it locally, push, pull on the remote, init-and-run.

**Separation of concerns.** Three hard boundaries:

- **legoESM** (model code) → lives at `../legoESM`, never edited here
- **legoESM-ocean-runners** (templates & runners) → lives at
  `../legoESM-ocean-runners`, never edited here
- **Output data** (NetCDF, Zarr, logs) → stored on HPC filesystems, never committed
  here; referenced by path in `experiment.tag`

**Analysis is a first-class citizen.** Per-experiment analysis scripts live
alongside their experiments in `runs/<nickname>_<date>_<desc>/`, making each run directory
self-contained. Reusable diagnostic functions and cross-experiment
intercomparison scripts live in `analysis/diagnostics/` and
`analysis/intercomparisons/` respectively. Jupyter notebooks are committed
with output cells stripped (via nbstripout).

## 3. Repository Map

```
runs/                One subdirectory per experiment — the core of this repo
  <nickname>_<YYYY-MM-DD>_<description>/
    run.yaml         Declarative intent (template, overrides, machine, status)
    config.yaml      Resolved configuration (generated by bin/run-experiment init)
    experiment.tag   Provenance record (generated by bin/run-experiment init; includes execution_hostname, execution_date after run)
    notes.md         Free-form human notes on setup, results, observations
    *.py / *.ipynb   Analysis scripts and notebooks (self-contained, run_dir = Path(__file__).resolve().parent)
    *.png            Output images from analysis scripts (committed — small, enables GitHub rendering)
    *.nc / *.npz     Model output data (git-ignored — never commit)
    diagnostics.json Runtime diagnostics (git-ignored — never commit)

analysis/            Reusable diagnostics and cross-experiment intercomparisons
  diagnostics/       Importable functions for computing physical quantities (MLD, heat content, etc.)
  intercomparisons/  Scripts comparing multiple experiments

reports/             Dated, shareable experiment-series reports
  <YYYY-MM-DD-description>/
    series.yaml      Experiment series manifest (runner_tag, machine, experiments)

machines/            Personal machine configurations (tracked here, not in runners)
  _template.yaml     Schema reference
  <machine>.yaml     Actual configs (may contain absolute paths — OK here)

bin/
  run-experiment     CLI helper bridging this repo to legoESM-ocean-runners
  lego-detect-machine  Auto-detect current machine by hostname, print info, write machine YAML with --write
  setup-workspace    Symlink workspace-conventions.md to the workspace root as AGENTS.md
  check-workspace    Validate workspace layout (repos, symlink, version alignment)

patches/             Personal patches to legoESM (if needed)

plans/               Pre-experiment planning documents
```

## 4. Boundaries

### What this repo IS

- A ledger of experiments: intent, configuration, provenance, and human notes
- A home for analysis scripts and notebooks
- A place to track personal machine configurations
- A synchronisation layer between development and HPC machines

### What this repo is NOT

- **Not the model.** legoESM source code is never edited here.
- **Not the runners.** Templates, runners, and their scripts live in
  `../legoESM-ocean-runners`. If a template or runner needs changing, do it there.
- **Not a data store.** No NetCDF, Zarr, or large binary files. Output data lives
  on HPC filesystems and is referenced by path in `experiment.tag`.
- **Not a fork.** This repo depends on legoESM and legoESM-ocean-runners as sibling
  directories. It does not vendor or duplicate their code.

## 5. Experiment Naming Convention

Every experiment directory follows the pattern:

```
<nickname>_<YYYY-MM-DD>_<description>
```

- **`<nickname>`** — short machine nickname from `machines/<machine>.yaml` `nickname` field
  (e.g., `laptop`, `cluster`)
- **`<YYYY-MM-DD>`** — date the experiment was declared/created
- **`<description>`** — short hyphen-separated description of the experiment

This naming convention encodes the execution machine directly in the directory name,
making it immediately clear where an experiment ran and when it was set up.

## 6. The `run.yaml` Format

Every experiment directory must contain a `run.yaml`. This is the file you author
to declare intent:

```yaml
template: ocean/baroclinic_gyre   # Template name from legoESM-ocean-runners
machine: my-machine                      # Machine YAML filename (matches machines/<name>.yaml). Optional — defaults to auto-detection via hostname
overrides:                                # Dot-notation overrides passed to init
  grid.resolution: 128x256
  ocean.A_h: 1e6
  time.duration_days: 730
status: planned                           # planned | submitted | running | completed | failed
```

**Field rules:**

- `template` — required. Runners-owned templates live in
  `../legoESM-ocean-runners/templates/`; graduated templates (cases
  maintained in legoESM's own template library) resolve by canonical name
  `ocean/<stem>` — pre-graduation names like `3d_idealized/baroclinic_gyre`
  still resolve as legacy aliases. See the runners README for the browsable
  list.
- `machine` — optional. YAML filename in `machines/` (without path). If omitted,
  auto-detected from the current hostname using `bin/lego-detect-machine`.
- `overrides` — optional. Dot-notation keys matching the template YAML structure.
- `status` — required. One of: `planned`, `submitted`, `running`, `completed`, `failed`.
  Update this as the experiment progresses.

## 7. Working Conventions

### Cross-Machine Workflow

1. **Design locally**: Write `runs/<nickname>_<date>_<desc>/run.yaml`, commit, push
2. **Execute remotely**: Pull, run `bin/run-experiment init runs/<nickname>_<date>_<desc>/`,
   then `bin/run-experiment run runs/<nickname>_<date>_<desc>/` (machine auto-detected
   from hostname), update `status` in `run.yaml`, commit and push
3. **Review locally**: Pull, read `experiment.tag` and `notes.md`, write analysis
   scripts in the run directory

### `bin/run-experiment` Commands

- `init <run-dir>` — Reads `run.yaml`, calls the runners' init with `--output-dir`
  pointing to the run directory
- `run <run-dir>` — Executes the experiment via the runners; on success, writes
  `execution_hostname` and `execution_date` to `experiment.tag`
- `record <run-dir>` — Re-generates `experiment.tag` from the current state
- `reproduce <run-dir>` — Calls the runners' `reproduce.py` using the committed
  `experiment.tag`

### `bin/lego-detect-machine` — Machine Auto-Detection

Auto-detects the current machine by matching `hostname -s` against `hostnames` lists
in all `machines/*.yaml` files.

```bash
bin/lego-detect-machine                     # Print detected machine info
bin/lego-detect-machine --write             # Write a machine YAML file
bin/lego-detect-machine --nickname foo      # Override nickname for --write
bin/lego-detect-machine --machine bar.yaml  # Specify machine YAML filename for --write
```

Used internally by `bin/run-experiment` when `machine` is omitted from `run.yaml`.

### Machine Configs

Machine YAML files live in `machines/` in this repo (not in the runners repo).
They may contain absolute paths and personal settings — this is acceptable here
because the repo is personal. The `bin/run-experiment` script passes the machine
config path to the runners when initialising an experiment. See `machines/_template.yaml`
for the full schema.

### Analysis Scripts and Notebooks

- Per-experiment analysis scripts and notebooks go in `runs/<experiment-name>/`,
  making each run directory self-contained. Use `Path(__file__).resolve().parent`
  as `run_dir` in these scripts.
- Reusable importable functions for computing physical quantities (MLD, heat content,
  etc.) go in `analysis/diagnostics/`. Functions take `xarray.Dataset` as input,
  return computed quantities, and have no side effects.
- Cross-experiment intercomparison scripts go in `analysis/intercomparisons/`.
- Notebooks are committed with output cells stripped (nbstripout pre-commit hook).
- Use paths from `experiment.tag` to locate output data — never hardcode
  machine-specific absolute paths in analysis scripts that should be portable.

## 8. What Agents Should Do

### Create a new experiment

1. Determine the machine nickname from `machines/<machine>.yaml` `nickname` field
   (or run `bin/lego-detect-machine` to auto-detect)
2. Create `runs/<nickname>_<YYYY-MM-DD>_<description>/run.yaml` with `template`,
   `machine` (optional — auto-detected if omitted), `overrides`, `status: planned`
3. Verify the template exists in `../legoESM-ocean-runners/templates/`
4. Optionally create `runs/<nickname>_<YYYY-MM-DD>_<description>/notes.md` with context
5. Do NOT run `bin/run-experiment init` — that is the user's responsibility on the
   target machine

### Record results for a completed experiment

1. Verify that `config.yaml` and `experiment.tag` exist in the run directory
2. Verify that `experiment.tag` contains `execution_hostname` and `execution_date`
3. Update `status` in `run.yaml` to `completed` or `failed`
4. Do NOT edit `config.yaml` or `experiment.tag` — these are generated files
5. The user may ask you to help write `notes.md`

### Add analysis for an experiment

1. Create scripts/notebooks in `runs/<experiment-name>/` — use
   `Path(__file__).resolve().parent` as `run_dir`
2. For reusable diagnostic functions, add them to `analysis/diagnostics/`
3. For notebooks: ensure nbstripout is active (output cells will be stripped on commit)
4. Use paths from `experiment.tag` to locate output data — never hardcode

### Help reproduce a past experiment

1. Read the `experiment.tag` in the run directory
2. Run `bin/run-experiment reproduce runs/<nickname>_<date>_<desc>/`
3. This checks out the correct runner tag, legoESM commit, and applies patches

## 9. What Agents Must NOT Do

- **Never edit `../legoESM/`** — the model code is not touched from this repo
- **Never edit `../legoESM-ocean-runners/`** — templates and runners are changed in
  their own repo; this repo only *consumes* them
- **Never commit data files** — no NetCDF, Zarr, or large binaries (small PNG images
  are the exception)
- **Never modify generated files** — `config.yaml` and `experiment.tag` are outputs of
  `bin/run-experiment init`. If they are wrong, fix the `run.yaml` and re-init.
- **Never commit an experiment directory missing provenance** — after an experiment has
  been run, `config.yaml` and `experiment.tag` must exist before committing. A
  `run.yaml` alone is only acceptable for `status: planned` experiments.
- **Never hardcode machine-specific absolute paths** in `run.yaml` or analysis scripts
  that should be portable. Machine-specific paths belong in `machines/*.yaml`.
- **Never commit notebook output cells** — nbstripout handles this, but verify if
  manually creating notebooks
- **Never delete `experiment.tag` files** — they are the permanent provenance record
- **Never change `status` in `run.yaml` without user confirmation** — status reflects
  the real-world state of the experiment
- **Never run experiments automatically** — always wait for the user to decide when
  and where to execute
- **Never commit an experiment with `runner_tag = untagged`** after the experiment has
  been completed — regenerate the tag to ensure the reproducibility chain is intact
